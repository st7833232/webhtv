- 狀態：階段一（只出設計），本文件送 Reviewer 審，之後 Manager 給使用者核准。階段二才改 `kkys.py` 並在兩平台實播。

## 1. 問題與根因（摘要）
- 詳細證據：`.herdr-synapse/webhtv-dev/artifacts/w233-kkys-ad-skip/報告.md`。
- FF 線路是 ffzy CDN 的直連 m3u8（`vip.ffzy-plays.com/<日期>/<id>/index.m3u8` → `3000k/hls/mixed.m3u8`）。
- CDN 在片中**固定時間**插兩支廣告：
  - 廣告 A：5 段，19.63 秒，在約 5:56 和 60:35。
  - 廣告 B：4 段，17.36 秒，在約 28:16 和 95:53。
- Android `HlsAdsParser` 與 iOS 移植版都沒有偵測到：8 個可疑區塊超過 122.7 分鐘片長的上限 6。

## 2. 做法：腳本內的本機代理
### 流程
1. `playerContent`：只在 FF 線路、而且站方給的位址是 `.m3u8` 時，回傳
   `self.getProxyUrl() + "&type=ffm3u8&url=" + quote(原位址)`，`parse: 0`，header 不變。
   - 其他線路、或沒有拿到 m3u8，照舊回原位址，行為不變。
2. 播放器向本機代理要清單 → `localProxy(params)`：
   - `type=ffm3u8`：用 `self.fetch` 抓 `url`。
     - 如果是 master（有 `#EXT-X-STREAM-INF`）：把每個 variant 的 URI 改成絕對位址，再包成同樣的代理位址，原樣回傳。
     - 如果是 variant：先把每段改成絕對位址（清單改從 127.0.0.1 送出，相對路徑會失效），再交給 `strip_ffzy_ads` 刪廣告，回 `[200, "application/vnd.apple.mpegurl", 文字]`。
   - 影片段（`.ts`）不經代理，播放器直接向 CDN 抓。代理只處理兩份小文字檔（約 17–200 KB）。

### 兩平台都支援這條路徑（程式位置）
- **Android（FongMi）**
  - `chaquo/src/main/python/base/spider.py:114` `getProxyUrl()` 回 `Proxy.getUrl(local)?do=py`。
  - `app/src/main/java/com/fongmi/android/tv/server/process/Proxy.java:35` 接 `/proxy` 請求，交給 `BaseLoader.proxy`。
  - `app/src/main/java/com/fongmi/android/tv/api/loader/BaseLoader.java:82` 依 `do=py` 交給 `PyLoader.proxy`，再交給**最近使用的 PY 站**（`PyLoader.java:56`）。
  - `chaquo/src/main/java/com/fongmi/chaquo/Spider.java:89` 呼叫 Python `localProxy`，回傳格式 `[狀態碼, MIME, 內容, 標頭?]`。
  - `Proxy.java:80` 任意 100–599 狀態碼都照實回傳，標頭也照帶，所以 302 退路可用。
  - 上面是本 repo 的 FongMi 程式碼（`origin/main`）。官方 APK 用的是同一套 pyramid／chaquo 路徑；階段二用 5560 上的官方 FongMi 實播確認。
- **iOS（WebHTV，W-202 起，`RuntimeABI` js.host 1.6）**
  - `ios/WebHTVApp/Python/base/spider.py:248` `getProxyUrl()` 回與 Android 相同的 `http://127.0.0.1:9978/proxy?do=py`。
  - `ios/Sources/WebHTVCore/SourceClient.swift:139` `servingAndroidProxy`：任何 9978 開頭的播放位址都改寫成 App 自己的 loopback 埠（含每次啟動產生的 token），不限 DASH。
  - `ios/Sources/WebHTVCore/Spider/SpiderProxyServer.swift:243` 只接 `do=py`／空值，交給最近一次改寫位址的 PY 站（與 Android 相同）。文字回應裡的 9978 前綴也會被改寫（同檔開頭說明）。
  - `ios/WebHTVApp/Python/webhtv_runtime.py:141` 把 `localProxy` 的回傳交給 Swift。
  - 風險：iOS 目前只實播過 YouTube 的 DASH 走這條路，**HLS 經代理還沒實播過**。階段二第一個驗證點就是它。

## 3. 廣告判定規則 `strip_ffzy_ads(text)`
### 設計原則
- 自成一段、不依賴其他模組的函式（只用 Python 標準庫），其他 FF 線路的 PY 站可以整段複製套用。
- 原型：`artifacts/w233-kkys-ad-skip/design/tools/ffads.py`，約 100 行。

### 步驟
1. 不是 VOD（沒有 `#EXT-X-ENDLIST`）、或區塊少於 3 個 → 原樣回傳。
2. 以 `#EXT-X-DISCONTINUITY` 切成區塊。**最後一塊一律不判**，與 Android 相同。
3. 找候選。ffzy 有兩種排法，各自判斷：
   - **規則排法**：正片每 N 段（實測 N＝5）就切一次，且 N 段的區塊佔一半以上。少於 0.75×N 段的**相鄰區塊合併成一段候選**，所以一支廣告被切成兩塊時，只算一次。
   - **長區塊排法**：區塊少、正片區塊很長。候選是夾在兩個超過 60 秒區塊之間、本身 ≤ 60 秒的單一區塊。
4. 候選總長 ≤ 60 秒，而且至少符合下列一項，才當廣告：
   - **K 已知廣告**：整段的段長序列（四捨五入到 0.01 秒）等於已知的 ffzy 廣告：
     - A：`4.87, 3.33, 6.37, 2.10, 2.97`
     - B：`6.96, 4.00, 2.56, 3.84`
   - **R 重複**：同一串段長在這份清單的候選中出現 2 次以上。
   - **F 幀率不符**：先從非候選的正片段推出正片幀率（23.976／24／25／29.97／30／50／59.94／60 中，有 90% 以上的段長是整數幀的那個）。候選裡超過一半的段不是整數幀，就算幀率不符。
5. 安全上限：要刪的總秒數超過片長 5%，就判定不準、原樣回傳。
6. 刪除時，連同那幾段的 `#EXTINF` 和候選本身的 `#EXT-X-DISCONTINUITY` 一起刪；下一塊正片自己的 `#EXT-X-DISCONTINUITY` 保留。其他標籤（包括 `#EXT-X-KEY`）都不動。

### 三種證據的分工（實測）
- K 單獨就認得出全部 34 次廣告。
- R、F 是給「廣告素材換了、K 失效」時的備援：
  - F 在正片幀率與廣告不同時有效（A 是 30fps、B 是 25fps）。
  - R 在同一支廣告插兩次時有效（長片）。
  - 如果只靠 R＋F，會漏掉 9 次：25fps 劇集只出現一次的 B，以及 30fps 動畫的 A。漏掉＝照舊播廣告，不會誤刪。
- K 的維護成本：ffzy 換廣告素材後要更新那兩行常數，沒更新時退回 R／F。

## 5. 失敗退路
| 情況 | 處理 | 使用者看到的 |
|---|---|---|
| 判不準（不是 VOD、排法不符、超過 5% 上限、沒有證據） | 回原清單（只把相對路徑改成絕對） | 跟現在一樣，有廣告 |
| 抓清單失敗或例外 | 回 `302`，`Location` 是原位址 | 播放器直接播原位址，跟現在一樣 |
| 代理被別的 PY 站搶走（兩平台都交給「最近使用的 PY 站」） | 只影響起播當下的兩次請求；VOD 清單起播後不再重抓 | 極少見；會播放失敗，換線或重開即可 |
| `localProxy` 逾時（iOS 20 秒、Android 照 FongMi） | 同上，播放器報錯 | 重試 |

- 302 退路兩平台的代理都照實轉送（Android `Proxy.java:80`；iOS `SpiderProxyServer.swift:456` 帶回原狀態碼與標頭），但播放器會不會跟著轉址，要在階段二實測。不行就改成在 `localProxy` 內回原清單文字。

## 6. 對起播時間的影響
- 網路：抓 master 與 variant 本來就是播放器要做的事，只是改成腳本抓。多出來的只有本機 loopback 的往返，可以忽略。
- 處理：Mac 上 0.3–3.7 ms（最大 198 KB 清單）。手機上的 Python 估計慢 10 倍左右，約 40 ms 內（未實測，階段二量）。
- 跳過廣告後，片長變短 20–74 秒，播放器顯示的總長就是去掉廣告後的長度。
- 其他行為：
  - 觀看記錄存的是播放位置。代理後的時間軸少了廣告，從舊記錄續播時，最多會差到 74 秒。
  - iOS App 自己的去廣告偵測、Android ExoPlayer 的 `HlsAdsParser`，看到的是已經乾淨的清單，不會再刪。

## 7. 比較過的方案
| 方案 | 結論 |
|---|---|
| 不改 | 兩平台都播廣告（使用者已否決） |
| 改 App 偵測規則（相鄰區塊合併計數） | 使用者選擇先不碰 App；這個方向留給之後另外評估 |
| **腳本本機代理刪廣告（本設計）** | 兩平台共用、不用發 App 版本、可以單獨回滾 |
| 腳本直接回 data URI 或其他格式 | CatVod 的 `playerContent` 沒有通用支援，兩平台行為不一 |
