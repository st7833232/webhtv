# IOS-POC-57：「下載」分頁依影集分組

## Recovery anchor

- 目標：使用者 2026-10-11 要求「下載要用每個影集當群組 可以一鍵下載 刪除 暫停」，並補充是指底部的「下載」分頁。
- 使用者選擇（AskUserQuestion）：
  - 一鍵下載＝「繼續暫停／失敗的集數」（不重新讀取作品頁、不排入還沒下載的集數）；
  - 版面＝「全部改成依影集分組」。
- 狀態：Core 測試完成（Linux 138／138，突變 4／4）；App 端只能靠發布建置編譯，真機未驗證。
- 已隨 `0.1.72 (73)` 發布（run `38127624020`，tag `ios-v0.1.72-b73`），發布建置是 App 端第一次通過編譯。
- 下一步：使用者在真機確認。

## 1. 行為

- 「下載」分頁：
  - 上方保留「儲存空間」。
  - 下方每部作品一組（以 `historyKey` 分組，不同線路放在同一組，與「管理下載」、觀看記錄一致）。
  - 排序：有進行中的集數的作品在前，其次是有暫停或失敗的，最後是全部下載完成的；同類依片名。
  - 無法讀取的下載資料夾獨立成一區。
- 每組的標題列：
  - 片名、「共 N 集 · 已下載 a · 進行中 b · 需要處理 c · 大小」，有集數正在下載時顯示平均進度。
  - 點標題列展開或收合各集；各集沿用原本的列（狀態、進度、「…」選單、左滑刪除），只顯示集名。
  - 「…」選單：
    - 「全部暫停（N 集）」：排隊、準備中、下載中的集數；
    - 「全部繼續（N 集）」：暫停與失敗的集數；
    - 「刪除全部」：經過與單集相同的刪除確認，標題列出作品名、集數與大小。
  - 左滑標題列也可刪除整部。
- 預設收合。

## 2. 設計

- Core 新增 `OfflineTitleGroup`（`OfflineOptions.swift`）：分組、排序、`pausable`／`resumable`／`completed`／`bytes`。分組邏輯放在 Core 是為了能在 Linux 測試。
- 「全部暫停」先暫停排隊中的集數，再暫停執行中的。反過來的話，每暫停一集執行中的，排程就會讓同組排隊中的一集補上開始準備，接著又被暫停。
- 「全部暫停」「全部繼續」逐集呼叫既有的 `OfflineDownloadManager.pause`／`resume`，沒有新增 manager API；刪除走既有的唯一刪除入口與確認視窗。
- 不重新讀取作品頁，所以來源失效的集數「全部繼續」後的行為與單集「重新下載／繼續」相同（需要時重新解析）。
- 設計研究：這是以既有操作重新排列畫面，不涉及播放、網路、資料格式或相容性，版面由使用者選定；沒有另做外部研究。

## 3. 驗證

- Linux `swift test` 138／138。新增 `OfflineTitleGroupTests` 3 項：
  - `downloadsAreGroupedByTitleWithWorkUnderWayFirst`：同作品不同線路在同一組、依線路與集數排序、刪除中的不顯示、依狀態排序（片名刻意取與狀態相反的順序）；
  - `pauseAllTakesTheQueuedFirstAndResumeAllThePausedAndFailed`；
  - `pausingATitleNeverStartsOneOfItsQueuedEpisodes`：3 集下載中、1 集排隊，全部暫停後 4 集都暫停，排隊的那集從來沒有送出傳輸。
- 突變 4／4 被抓到：先暫停執行中的、保留刪除中的、不依狀態排序、集數排序忽略線路。「不依狀態排序」第一次沒有被抓到（測試片名的順序剛好等於狀態順序），改片名後抓到。
- 第一次完整執行時，新的整合測試因 5 秒等待逾時失敗；同一輪其他測試也都延遲約 5.4 秒才完成。單獨執行與之後兩次完整執行都通過，判斷為執行環境暫時停頓，不是程式問題；記錄於此。
- 未驗證：App 端畫面（展開、選單、左滑）沒有在真機或模擬器執行，只能靠發布建置編譯。
