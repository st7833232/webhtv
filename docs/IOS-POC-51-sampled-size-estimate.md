# IOS-POC-51：用實際片段大小預估下載容量

## Recovery anchor

- 目標：使用者回報「下載預計快 300MB，實際上是 7 百多」。之後選擇方案 A：下載前用實際片段推算大小，下載中依已下載的部分持續修正。
- 驗收標準：
  1. 開始下載前的預估改用片段實際大小。下載畫面顯示的數字和空間檢查用的數字相同；量不到片段大小時，退回片源宣告的位元率，並標明是宣告值。
  2. 下載中顯示的「已下載 X / 約 Y」，在已下載一成之後改用已下載片段推算的大小；並行下載的空間預留也改用這個數字。
  3. 抽樣只讀每個片段 1 byte，不下載片段本身；憑證只送往片源自己的主機，與下載的規則相同。
- 狀態：程式與 Core 測試完成（Linux 80／80，突變 6／6）。依使用者先前的指示「不要跑ci修改後就發佈」，不另跑 macOS CI。
- 下一步：發布 `0.1.65 (66)`。

## 1. 原因（以 `2db9e7e9` 為準）

- `OfflineMediaSelector.estimate`：預估 = 播放清單宣告的 `AVERAGE-BANDWIDTH`（或 `BANDWIDTH`）× 片長。片源宣告偏低時，預估就跟著偏低。使用者的例子宣告值只有實際的 4 成左右；這是從數字推論，沒有看到該片源的播放清單。
- 只有 media playlist、沒有 master 的片源，原本完全沒有預估，顯示「無法預估」。
- 空間檢查（`prepare` 的 `hasRoom`）與並行下載的空間預留都用這個預估，所以宣告偏低時，檢查也偏寬鬆。

## 2. 設計

- **抽樣（`sampledRate`、`segmentSize`）：**
  - 把片段平均分成 5 段，取每段中間那一個，不取開頭幾個，因為開頭常是片頭。
  - 5 個請求同時送出，每個帶 `Range: bytes=0-0`，從 `Content-Range` 的總長取得大小；若伺服器不支援 Range、回 200，就用 `Content-Length`。
  - 讀取上限 1 byte；有 byte range 的片段直接用它的長度。
  - bytes／秒 × 片長 = 預估；有獨立音軌時再加上音軌抽樣的結果。
  - 量不到任何大小時，退回宣告值。
- **新的預估來源 `OfflineSizeEstimate.Basis.sampled`：**
  - 顯示為「約 X」，下載畫面的註腳寫「依實際片段大小推算」；宣告值的註腳寫「依來源宣告的位元率，可能與實際不同」。
  - 舊版 App 讀到這個值時，會依既有的容錯解碼當成無法預估，不會讀不到整筆下載紀錄。
- **用在哪裡：**
  - `build()`（準備階段）：master 與只有 media playlist 的片源都改用抽樣結果。
  - `sizeEstimate(for:choice:)`：下載畫面用。內部走與準備階段相同的 `build()`（不含字幕），所以畫面上的數字就是空間檢查用的數字。
  - 畫面打開與切換畫質、音軌時重新量測，量測中顯示轉圈；按「下載」時用量到的數字做入列的空間檢查。
- **下載中修正（`OfflinePackagePlan.projectedBytes`）：**
  - 每個片段記錄自己的秒數（`OfflineDownloadUnit.seconds`，選填，舊的計畫沒有這個欄位）。
  - 依片段所在資料夾分成影片、音軌、字幕三條軌道，各自用已完成片段的 bytes／秒乘上該軌道的總秒數，再加上已下載的金鑰、init section。
  - 不同軌道分開算，避免把小的音軌檔也當成影片片段的大小。
  - 最長的軌道下載滿一成後才開始推算；還沒有完成片段的軌道暫時不計入，所以獨立音軌晚完成時，數字會略為偏低。
  - 計算結果存在 `progress.projectedBytes`，重開 App 後由磁碟上的檔案重新算出。
  - 「下載前預估」仍保留開始前的抽樣值。
- **並行預留：** `reservedBytes` 改用 `projectedBytes ?? estimate`。
- **與現有行為的關係：** 選版本的規則不變，仍依宣告值挑選。抽樣只影響顯示的大小與空間檢查。

## 3. 驗證

- Linux：80／80。新增 `OfflineSizeEstimateTests` 9 項：
  - 宣告 800 kb/s、實際片段每個 3 MB：預估從 4.8 MB 改為 24 MB，抽樣請求共 5 個，都帶 `bytes=0-0`；
  - 可用空間 510 MB 時，宣告值會通過、實際值不會：下載以 insufficientStorage 失敗；
  - 下載畫面的 `sizeEstimate` 等於準備階段的數字，且沒有產生任何下載紀錄；
  - 片段在其他主機時，抽樣請求不帶 Cookie、仍帶 User-Agent，master 請求仍帶 Cookie；
  - 片段不回報大小時，維持宣告值；
  - 只有 media playlist 的片源也有預估；
  - 影片與音軌各自依自己的速率推算；
  - 不到一成時不推算，舊計畫不推算；
  - 下載 1／4 後推算出整集大小，重開 App 後仍在。
- 突變 6／6 被抓到：
  - 只用宣告值；
  - 不帶 Range；
  - 跨主機送出全部 header；
  - 推算時不依時長放大；
  - 所有軌道算成同一條；
  - 重開後不重新推算。
- 編譯期間 `sampledRate` 的一行運算式在 Linux 上 type-check 逾時，已改為明確型別。App 端只經發布 workflow 的建置編譯。
- 未驗證：真機上各片源是否支援 `Range: bytes=0-0`（不支援時會退回宣告值）、下載畫面的量測延遲。
- Ponytail：unavailable / skipped。

## 4. 風險

- 開啟下載畫面時，每個畫質選擇會多出約 7–12 個小請求：probe、master、影片清單、音軌清單、5～10 個 1-byte 請求。
- 「全部下載」的每一集在準備階段也會做一次抽樣。
- 5 個樣本仍可能因片段大小不一而有誤差；下載滿一成後會由實際下載的片段修正。

## 5. Rollback

- revert 本 commit，預估回到宣告值。新增的欄位都是選填，資料格式相容。
